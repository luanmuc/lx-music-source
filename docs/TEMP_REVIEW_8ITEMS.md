## 一、原清单"不做"的 3 项

### 1. probe-history 30 天清理 —— 已经实现了，不需要再做

清单写"现状：`docs/probe-history.jsonl` 追加写，30 天以前的记录不清理"。**与代码不符**：

`scripts/probe.js:81-105`
```js
// v8.0：30 天滚动清理——只保留近 30 天数据，防止文件无限增长
const HISTORY_RETENTION_DAYS = 30;

```
`docs/AUDIT_PLAN.md:83` 亦有记录：`✅ v8.0 已加 30 天滚动清理（appendHistory 后过滤旧行重写文件）`。

**体积实测**：419 行 / 52KB / 10 天（41.9 行/天）→ 30 天窗口下稳定在 **约 1250 行 ≈ 150KB**。public 仓库体积不构成问题，且清理只影响未来（git 历史里旧数据仍在，删了也不减仓库体积）。

**唯一可议**：41.9 行/天来自每天 3 轮巡检 × 15 端点；若要更小可减到每天 1 轮，但会削弱近 7 日聚合与告警灵敏度的采样密度 —— 收益不抵损失，不做。

### 2. half-open 成功先降后批 —— 不做（前提不成立）

清单疑虑是"源刚恢复就又挂 / CDN 缓存命中导致 half-open 假成功"。核实机制：**half-open 放行的是真实用户播放请求，不是探针**。

`lx-source.js:679-682`（`getBreaker`，在播放链路 `wrapExecute` 之前调用）
```js
if (b.state === 'open') {
  if (Date.now() - b.lastFailureTime >= cfg('breakerCooldownMs', 180000)) {
    b.state = 'half-open'; return true;   // 放行一次真实请求
```
`lx-source.js:696`（`recordSuccess`）
```js
if (b.state === 'half-open') { b.state = 'closed'; b.failureCount = 0; }
```

half-open 的"试探成功"= 一次真实取链交付成功。每次取链拿到的都是新 URL，不存在"旧 CDN 缓存命中 → 假成功"的路径。要引入"半开降批"就得在熔断核心加第三态（open / half-open / half-open-degraded / closed），而震荡已有三道门抑制：`PROBE_FAIL_REQUIRED=2`、`PLAY_DEAD_STREAK>=3` 摘链、`PLAY_DEAD_REVIVE` 复活。

另：**熔断状态只存内存、不落盘**，客观上不存在可统计的"反复横跳"证据——为一个无证据的假设去改状态机，风险远大于收益。

### 3. UA 池 4 → 8~10 套 —— 不做（403 不是 UA 造成的）

清单问"有没有源因 UA 被风控 403/429"。实测 10 天失败原因分布：

```
ENOTFOUND 58 | HTTP 403 36 | HTTP 404 32 | TIMEOUT 18 | HTTP 429 12 | HTTP 503 10
```

403 高度集中在两个已知受限接口：
- `oiapi.net/api/QQ_Music`：**22 次**（QQ 接口封禁，已知死源）
- `music-api.gdstudio.xyz`：**14 次**（免费额度风控）

这两处是**接口策略/配额限制**，不是浏览器指纹识别。且现有 `getMobileUserAgent()` 本身按分钟轮换（`__uaCounter++ + Math.floor(Date.now()/60000)`），若 UA 是变量，403 会抖动而不是稳定出现。

**证据方向与"扩池"相反**：这两处换 UA 不会变好。清单自己也写了"凑上游真实在用的移动端 UA 难"，堆假 UA 只会提高被识别概率。无实测痛点前不做。

## 二、原清单"不动"的 2 项

### 4. gdWy 升首批 —— 不做，十天里六天 403

清单问"配额到底有多紧"。实测 `music-api.gdstudio.xyz` 逐日可用性：

```
10-28 ❌403  10-29 ✅  10-30 ❌403  10-31 ❌403  11-01 ❌403
11-02 ❌403  11-03 ❌403  11-04 ✅     11-05 ❌403  11-06 ✅
                                            可用率 4/10
```

而 handler 注释写明它是 **5min/50 次**配额源（`SOURCE_HANDLERS.gdWy.batch: 2`）。

**升首批的代价**：wy flac 每次都要吃 300ms 错峰等它，而它有 60% 概率直接 403 —— 等于给 wy flac 常态化加 300ms 空转并发位。当前"前批全败才打它"恰好把低可用率隔离在兜底层，是正确设计。

**本条应改为"维持不动"，且现有数据是维持的实证支持。**

### 5. 版本串三处自动生成 —— 不做（只能自动化 1/3，且门禁已兜住）

三处实际位置：`@description`(L3)、`@version`(L4)、`logInfo`(L2494)。

关键事实：L3/L4 装的是**一整段变更史长文本**，且是文件头注释，运行时代码无法引用；能抽常量复用的只有 `logInfo` 一处。所以"自动生成"最多覆盖 1/3，另 2/3 仍需手写。

而 `scripts/self-check.js` 已校验三者一致、不一致即 CI 阻断 —— v8.9 那次 CI 变红正是它按设计工作。也就是说"忘改"的后果是**发布被拦**，不会带病上线。

若硬要做，只能写"构建时改写文件头注释"的脚本，代价是每次发布都动 L3/L4 的超长行、diff 噪音大、review 可读性下降 —— **净负收益**。不做。

## 三、原清单"筛掉"的 3 项

### 6. 熔断冷却 3min 太短 —— 不做（同第 2 条，机制已保证）

`BREAKER_COOLDOWN_MS = 180000`(3min)，到期后第一次请求进入 half-open，成功即 closed。

"CDN 假成功"前提不成立（见第 2 条：half-open 走真实取链，URL 每次新生成）。3min 本身就是快速恢复的取舍：太长会让源恢复后用户长时间取不到，太短只影响一次请求判定，且失败会立刻回到 open。**保持不动。**

### 7. LRU 500 条太小 —— 不做（6 小时内要听满 500 首才会挤）

`CACHE_MAX_SIZE = 500`（`lx-source.js:59`），成功缓存 TTL 6h（高音质 30min）。

500 条 / 6h = **每 43 秒一首**才可能挤掉。更关键：LRU 淘汰的后果只是**重新取链**（多 1~2s），不是播放失败 —— 属性能损耗，非可用性故障。

真要可配，把它接进 `USER_CONFIG` 是一行的事，但当前没有实测瓶颈支撑，调大反而增加内存与过期死链命中面。不做。

### 8. 探测歌曲池 12 首 —— 不做（误判需要连续两轮抽到同一首坏歌）

`PROBE_SONG_POOL` 12 首：晴天/海阔天空/稻香/青花瓷/七里香/夜曲/后来/光年之外/演员/平凡之路/成都/小幸运 —— 全是各平台都有版权的国民级曲目。

叠加三重防护：
1. `PROBE_PASS_REQUIRED = 2` / `PROBE_FAIL_REQUIRED = 2`：连续两轮一致才切换 → 单曲误判需连续两轮抽中同一首坏歌，概率 **1/144**；
2. `isAudioPlayable` Range 206 + 魔数二次校验；
3. v8.0 起 helloworld 等源有试听片段关键词检测（preview/test/sample/试听）。

三重防护下"因探测歌无版权/是试听片段而误判死源"基本不可达。不做。
