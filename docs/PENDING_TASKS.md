两仓库审计已收官（source 40 维 / mobile 39 维全绿）。审计发现：仓库大量**高频操作依赖个人经验与记忆**（修源取证、上游合并、跨仓库同步），每次重复摸索。现将三类操作沉淀为**可查手册**。

**共同原则（三件事都必须遵守）**：
1. **活文档**：骨架先立完整，真实案例随实战回填（修一次、回填一行），不是一次写死的百科
2. **可执行**：每个模式/条目都带"症状→定位→解法"或等价的可照做结构，协作方（另一账号/新会话）读一遍即可上手
3. **引用联动**：建好后在对应仓库的 README 或主指南（DEV_GUIDE / MERGE_GUIDE / MUSIC_SOURCE_GUIDE）中加一行引用，让后来者找得到

## Task 1：接口变更应对手册（source 仓库）—— 含候选实证取证

**目标文件**：`lx-music-source/docs/INTERFACE_CHANGE_PLAYBOOK.md`（新建）

**背景**：音源挂掉 90% 是平台改接口。修复工作永远是"看请求→看响应→对比新旧→识别变更类型→套解法"，目前全凭现场摸索。手册把六类高频变更模式查表化，同时服务两个场景：**修源取证**（源挂了查原因）+ **候选实证取证**（新候选判活判否，与 huanyin 判否同款动作）。

**文档结构要求**：

1. **六类变更模式速查表**（三栏：症状 → 快速定位 → 解法示例），模式必须覆盖：
   - 签名/鉴权类（平台加 sign/token/eapi）——症状：401/403/返回空
   - 字段改名类（songmid→rid 等）——症状：能搜到歌、取不到链
   - 域名/防盗链类（换域名、CDN 校验）——症状：连接失败/403
   - 响应格式类（XML↔JSON、单引号、编码）——症状：解析失败
   - 音质档位变化类（flac 停供、320k 改名）——症状：降级链异常
   - 风控限流类（IP 被限、业务 502）——症状：间歇失败/业务错误码
2. **共用取证工具表**（修源取证与候选实证共用）：
   - 域名是否可解析：`dig +short <domain>` / `nslookup`（NXDOMAIN = 域名失效型）
   - 原始响应体：curl 抓真实请求响应（看业务码/字段结构，不看摘要）
   - 响应头/格式：content-type、首字节（判断 XML/JSON/编码）
   - git log 对比：`git log -p --follow` 看该源最近改动，判断"刚改过才挂"或"长期未动突挂"
3. **首批真实案例库**（从实际经历提炼，每例写"症状→定位过程→结论/解法"）：
   - huanyin 判否（2026-11-05）：music-dl.sayqz.com DNS 不可解析（域名失效型）+ api.xcvts.cn 返回咪咕 502"服务器 IP 可能被咪咕限制"（风控限流型）——双通道失效，判否
   - ecosystem-scan 404（2026-11-05）：pdone 仓库改名 backend-api→lx-music-source，健康表 URL 未同步——分发层变更型（可并入域名/分发类说明）
   - 酷我搜索接口单引号 JSON 响应（abslist 结构）——响应格式型示例（smoke-test T13 已覆盖）
   - 咪咕风控 502 特征（错误信息明确提示 IP 被限）——风控限流型示例
4. **回填机制说明**：每次真实修复后在案例库追加一行（症状→定位→解法），保持活文档

**验收标准**：六类表完整可查；取证工具表 ≥4 条标准动作；真实案例 ≥3 个；DEV_GUIDE 或 README 中有一行引用本手册。

## Task 2：上游合并冲突速查（mobile 仓库）

**目标文件**：`lx-music-mobile/docs/MERGE_CONFLICT_PLAYBOOK.md`（新建；也可并入现有 MERGE_GUIDE.md 作为独立章节，二选一，但必须独立成节、标题清晰）

**背景**：mobile 每次合并上游（如 v1.9.2 合并）都会遇到同一批冲突文件（上游改、定制也改的位置），现在每次现场解。沉淀"常见冲突点 + 标准解法"压缩合并时间。

**文档结构要求**：
1. **常见冲突点清单**（≥5 条，从 v1.9.2 合并经验提炼），每条含：

2. **合并流程速查**：从拉上游 tag → merge → 解冲突 → 版本号升级 → 文档同步的要点（可引用 RELEASE_SOP/MERGE_GUIDE）
3. **回填机制说明**：每次合并后追加新冲突点

**验收标准**：冲突点清单 ≥5 条且每条可照做；MERGE_GUIDE 或 RELEASE_SOP 中有一行引用。

## Task 3：音源能力 → App 配套同步点总表（跨仓库）

**目标文件**：`lx-music-mobile/docs/SYNC_POINTS.md`（新建，面向 mobile 维护者；音源侧引用时指向本表）

**文档结构要求**：
1. **同步点总表**：音源能力项 → App 需同步的位置（文件路径 + 具体位置）→ 检查动作。首批覆盖：
   - 音源 action（8 个：musicUrl/lyric/pic/health/toggle/probe/config/trend）→ userApi switch case + MUSIC_SOURCE_GUIDE action 表

2. **迭代后检查流程**：音源发布新版本后按本表逐行核对（可作 checklist）
3. **回填机制说明**：每次发现新同步点追加一行

**验收标准**：总表覆盖上述全部已知同步点；每行有具体文件路径；README 或 DEV_CONVENTIONS 中有一行引用。
